# 字幕意群重切分技术方案

本文档说明 `src/common/utils/subtitle/meaning-group-segmenter.ts` 的意群重切分（meaning-group
re-segmentation）技术方案：它解决什么问题、算法原理是什么、参数如何取值、与翻译链路如何衔接。

## 1. 问题：滚动式碎片字幕

YouTube 对没有作者字幕的视频用 ASR 自动生成英文字幕。其原始形态（yt-dlp 下载到的
`en-orig` 轨）是**滚动式碎片 cue**，有三个特征：

1. **时间轴重叠**：后一条 cue 的开始时间早于前一条的结束时间（前句尾部与后句头部同屏滚动）；
2. **句子拦腰切断**：cue 边界与语义边界完全不对齐，`Today, you and I are going to talk about`
   / `a topic that I get a ton of questions` 是两条独立 cue；
3. **无句末标点**：ASR 不产标点，`>>`（换人）与 `[music]`（背景音）是仅有的标记。

碎片 cue 直接用作学习产品的字幕行时，三个消费方同时受害：

| 消费方 | 碎片行的问题 |
| --- | --- |
| 字幕翻译 | 逐碎片送翻译，模型拿到 `you are` 这类半截输入，译文必然不可靠 |
| 精听循环 | 单句循环停在半个意群，听的是残句 |
| 侧栏字幕列表 | 列表以行显示，碎片行不可读 |

本方案在**数据解析层**把碎片重切分成完整意群——一处修复，翻译、精听、显示全部受益。
（此前的"整句模式"是前端显示层缝合，仅解决展示与导航；数据层修复后它自动退化近似恒等，保留作兜底。）

## 2. 大白话原理

把每条 cue 想成一截录音带的文字稿，重切分就是三步：

1. **拆**：每条 cue 内部先按"句号/问号/感叹号"和 `>>`（换人）切成小段；
2. **拼**：按时间顺序把小段往一个"当前句缓冲"里放——只要缓冲里的句子还没被标点收束、
   下一段来得不太迟（间隔 < 0.8 秒）、缓冲也没超长，就继续拼；否则封句、开新句；
3. **摊时间**：拼接出来的句子横跨多条 cue、时间轴还有重叠，句子内部每段的时间按
   **字符数占比**线性插值摊回 [句子起点, 句子终点]。

一句话概括：**标点说了算，停顿辅助判，长度兜底防巨块（强切时回溯到最近的逗号），时间按字数摊。**

## 3. 算法流水线

入口：`resegmentIntoMeaningGroups(lines: SrtLine[]): SrtLine[]`（纯函数，无 I/O）。

### 3.1 防御性跳过

- 空数组原样返回；
- **任一行的 `contentZh` 非空 → 整体原样返回**：人工对齐的双语文件一旦重切分，中英行
  对应关系必然错位，宁可不做。

### 3.2 cue 内拆分（`splitLineIntoPieces`）

对每条 cue 的 `contentEn`：

1. 用 `TERMINAL_PATTERN = /[.!?…]+["'”』」)\]]?/g` 找出全部句末标点位置（允许 `."`、`?"`
   这类收尾引号；省略号算收束）；
2. 用 `SPEAKER_MARK_PATTERN = /^\s*(>>\s*)+/` 补充切点（cue 开头的说话人标记视为句边界，
   且标记文本本身从片段中剥离——对学习者是噪音）；
3. 按切点分段，每段时间 = `cue.start + duration × (字符偏移 / 总字符数)`；
4. **最小时长兜底**：插值可能产出过短的子区间（低于 0.2s），向相邻段借时长，保证
   时间轴严格递增（`srtLineToSentence` 对 `end <= start` 会抛错）。

### 3.3 跨 cue 归并（主循环）

维护一个句缓冲，对每个时间片段依次判定是否开启新意群：

```
开新意群 ⇔ 缓冲为空
        或 缓冲文本已被句末标点收束（endsWithTerminal）
        或 片段起点 − 缓冲终点 ≥ 0.8s（说话停顿）
        或 缓冲字符数 + 本片段字符数 > 250（防巨块）
```

否则并入缓冲（文本以空格连接，`end` 延伸到片段终点）。

注意封块条件用的是「并入后超出上限」而非「已达到上限」——否则恰好 250 字的块永远
无法再并入任何后续片段，产生人为碎句。

**上限强切的逗号回溯**：默认切点是 cue 边界，而 cue 边界与语义无关，会把句子拦腰
斩断（真实案例，5yCqhY1D-VE：`… what activity they're`｜`going to do.`）。因此上限
触发的封句会先回溯到缓冲内**最后一个逗号**（列表/从句边界更接近语义边界），把逗号
后的尾巴连同触发片段留给下一组，分界时间按字符占比在缓冲区间内插值；唯一逗号贴近
开头（头部长度 < 60 字符）或没有逗号时，维持 cue 边界强切。停顿封句不做回溯——
停顿本身是语义信号，回溯会把停顿卷进意群内部。

### 3.4 输出

所有缓冲按序输出为新的 `SrtLine[]`，`index` 从 1 重新编号，`contentZh` 置空（等待翻译
链路按意群为单位生成）。

## 4. 关键参数

| 参数 | 值 | 依据 |
| --- | --- | --- |
| `GAP_BREAK_SECONDS` | 0.8s | 说话人换气停顿的经验阈值；滚动字幕同句相邻 cue 间隔通常 < 0.3s |
| `MAX_BUFFER_CHARS` | 250 | 无标点段落（如整段口语）的强制封句上限，约 3-4 行字幕的量 |
| `MIN_SEGMENT_SECONDS` | 0.2s | 子区间最小时长，兼顾可点击性与时间轴严格递增校验 |
| `BACKTRACK_MIN_HEAD_CHARS` | 60 | 上限强切回溯逗号时的最小头部长度；头部太短宁可不回溯 |

调优建议：意群偏碎 → 增大 `GAP_BREAK_SECONDS`；出现跨长段落的巨型合并 → 减小
`MAX_BUFFER_CHARS`。改动纯函数行为后记得跑
`src/common/utils/subtitle/__tests__/meaning-group-segmenter.test.ts`（9 个用例覆盖
碎片归并、cue 内拆分 + 插值单调、`>>` 边界、间隙封句、上限强制切、双语跳过、单句恒等、
真实 YouTube 样本）。

## 5. 接入点与缓存

### 5.1 接入点

`SubtitleServiceImpl.parseSrt`：`parseSrt/parseAss` 产出 `SrtLine[]` 之后、
`srtLineToSentence` 之前插入 `resegmentIntoMeaningGroups`。开关
`subtitle.meaningGroupResegmentation`（sysConf，未写入视为开启）实时读取。

`SplitVideoService` 直接调用 parser 纯函数（导出字幕保持原始 cue），不受影响。

### 5.2 缓存键设计（重要，曾出过回归）

解析结果缓存于 `cache:srt`，**键一律是裸 `fileHash`**——翻译调度器
（`update-subtitle-demand`）、收藏片段、聊天会话、学习页等消费方全部按裸 `fileHash`
读取。键里掺任何前缀（如曾经的 `mg:`）都会让这些消费方整体 miss，播放页报
「未找到字幕缓存」（e26f4029 修复的回归）。

意群开关状态的缓存一致性靠**值内标记**：缓存条目带 `resegmented` 字段（写入时的开关
状态），命中时与当前开关比对，不一致视为 miss 重建。这样：

- 「切换开关 → 重开视频生效」语义不变；
- 不需要任何失效订阅；
- 增量转录 `buildSentencesFromLines` 写入的无标记条目视为未重切分，关闭开关时可正常命中。

### 5.3 翻译衔接

重切分后的行自带句末标点，是理想的翻译单元：本地链路（`local` provider）按 5 句一组
带上下文批量填槽翻译（GBNF 源文锚定，策略版本 v4，采样温度 0），译文以完整意群回填。
翻译缓存（`dp_sentence_translates`）按内容派生键，天然适配新行。

## 6. 下游影响与接受的代价

| 消费方 | 影响 |
| --- | --- |
| 侧栏列表 / 主字幕 / 移动端 | 自动适应（同源 sentences） |
| 前端整句模式（sentence-grouping） | 自动退化近似恒等（重切分行已带句末标点），保留作兜底 |
| 翻译缓存 | 旧碎片译文成孤儿行（无害，内容键不命中即弃） |
| 时间轴调整 / 配音 manifest | 按 fileHash-index 持久化，重切分后行号失配即失效——**接受** |
| 收藏片段 | clipKey 按 ±5 行内容 hash，身份漂移但旧数据无损可播 |
