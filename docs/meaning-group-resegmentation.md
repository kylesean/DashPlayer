# 字幕意群断句技术方案

本文档说明 `src/common/utils/subtitle/meaning-group-segmenter.ts` 的意群断句方案：
解决什么问题、算法原理、参数依据、与翻译/练习链路的衔接。

## 1. 问题：滚动式碎片字幕

YouTube 对没有作者字幕的视频用 ASR 自动生成英文字幕。其原始形态（yt-dlp 下载到的
`en-orig` 轨）是**滚动式碎片 cue**，有四个特征：

1. **时间轴重叠**：后一条 cue 的开始时间早于前一条的结束时间（同屏滚动）；
2. **句子拦腰切断**：cue 边界与语义边界完全不对齐；
3. **无句末标点**：ASR 常不产标点，`>>`（换人）与 `[music]`（背景音）是仅有的标记；
4. **重复尾巴**：滚动展示会让后一条 cue 重复前一条的后半句。

碎片 cue 直接作为学习产品的字幕行时，三个消费方同时受害：

| 消费方 | 碎片行的问题 |
| --- | --- |
| 字幕翻译 | 逐碎片送翻译，模型拿到 `you are` 这类半截输入，译文必然不可靠 |
| 精听循环 | 单句循环停在半个意群，听的是残句 |
| 侧栏字幕列表 | 列表以行显示，碎片行不可读 |

因此在**数据解析层**一次性重切成完整意群——一处修复，翻译、精听、显示全部受益。

## 2. 设计决策：不再提供开关

旧实现有「碎句字幕合并」（解析层）与「整句连读模式」（播放层）两个开关，规则高度
重叠，用户无法理解区别，且两个都开时前端归并近乎恒等、开关看起来毫无作用。

现在的原则：

- **完整意群是数据质量，不是用户偏好**：半句碎片对翻译与循环只有坏处，不提供关闭入口；
- **解析层统一断句**：`SubtitleService.parseSrt` 恒调用重切分，不再读系统配置；
- **播放层统一按意群导航**：跳转/循环/自动暂停/跟读一律以意群块为单位，
  `sentenceBlockMode` 字段与 UI 开关一并删除；
- 前端 `groupSentencesIntoBlocks` 保留，用于覆盖「人工字幕每行不足一句」的情况。

## 3. 算法流水线

入口：`resegmentIntoMeaningGroups(lines: SrtLine[]): SrtLine[]`（纯函数，无 I/O）。

### 3.1 防御性跳过

- 空数组原样返回；
- **任一行的 `contentZh` 非空 → 整体原样返回**：人工对齐的双语文件一旦重切分，
  中英行对应关系必然错位。

### 3.2 滚动去重（`rolling-dedup.ts`）

逐词比较相邻两行的尾巴/头部，剥掉重复部分：

- 只在**词边界**上比较，且要求重叠 **≥ 2 个词**——单字重叠（`a`、`I`）在自然语言里
  极其常见，按它去重会误删真实内容；
- 比较前逐词归一化（小写、剥首尾标点），`about.` 与 `about` 视为同一个词；
- 整行都是重复内容时丢弃该行，并把时长并入前一行，避免时间轴出现空洞；
- 只比较**相邻**行：跨行比较会把正文里反复出现的短语误判成重叠。

### 3.3 摊平与时间估算

把每条 cue 按 `>>` 切段，再切成词，然后在 cue 内部按**音节权重**插值时间：

```
word.start = cue.start + cueDuration × (前缀音节权重 / 总音节权重)
```

为什么用音节而不是字符：英文里音节数与发音时长的相关性明显强于字符数
（`strength` 8 字符 1 音节，`idea` 4 字符 3 音节）。音节用元音串计数近似，
并对词尾不发音的 `e` 做修正。

#### 3.3.1 有效发声窗口（cue 的 `end` 不可信）

**滚动字幕的 `end` 是「这行滚出屏幕」的时刻，不是「这句话说完」的时刻。**
实测一部 67 分钟的视频：956/960 条 cue（99.6%）的结束时间都晚于下一条 cue 的
开始时间，平均多出 **2.12 秒**。

如果直接拿 `end - start` 当发声时长，词时间会按比例被拉长，整句右移；下一行
又被「严格递增」钳制继续后推，误差逐句累积。用户看到的就是
**「字幕还停在上一句，音频已经说到下一句」**。

修法是先算有效发声终点，再插值：

```
若 下一条 cue 与当前 cue 滚动重叠（next.start < cur.end 且 next.end > cur.end）：
    speechEnd = next.start      // 同一时刻开始说下一句，说明这句最多说到那时
否则：
    speechEnd = cur.end
```

**必须区分「滚动重叠」与「插话嵌套」**。两者形态相似但语义相反：

| 形态 | 判据 | 处理 |
| --- | --- | --- |
| 滚动重叠 | 后一条压进前一条尾巴，且延伸到更后面 | 截断，占实测 954/956 |
| 插话嵌套 | 后一条完全落在前一条区间内（音效、旁人短句） | **不截断**，主句仍在继续 |

把插话当成滚动重叠去截断，会把主句压成插话的长度（测试里有专门用例钉住）。

### 3.4 全局动态规划

`bestCost[i]` = 切完前 i 个词的最小总代价；行首从 `i-1` 向左扩展，
硬约束（字符/时长/词数）越界即停止。总代价 = 断点代价 + 行代价：

**断点代价**（从强到弱）

| 信号 | 代价 |
| --- | --- |
| `>>` 换人 | 0 |
| 句末标点 + 下一词大写 | 0 |
| 句末标点 + 下一词非大写 | 12 |
| cue 间停顿 ≥ 0.6s | 20 |
| 逗号/分号/冒号 | 40 |
| cue 间停顿 ≥ 0.3s | 60 |
| 裸 cue 边界（无停顿信号） | 110 |
| cue 内部硬切 | 170 |
| **行尾悬空虚词** | **260** |

**行代价**

| 项 | 规则 |
| --- | --- |
| 阅读速度 | 超过 18 字符/秒 后按平方惩罚，封顶 300 |
| 短行 | 少于 24 字符，每字符 +6 |
| 长行 | 超过 110 字符后按平方惩罚（系数 0.02） |
| 行时长 | 超过 12 秒后每秒 +12 |
| 行内横跨停顿 | 每处 +220 |

**悬空虚词惩罚**是本次最关键的新增项。旧贪心算法最容易犯的错就是
`... are going to talk about` / `a topic that ...` 在 cue 边界被切开，
前半句停在一个介词上——这既不是一个意群，翻译模型也拿不到完整结构。
`DANGLING_WORDS` 收录冠词、介词、连词、代词、助动词、关系词；
句末标点结尾的词不算悬空。

### 3.5 强制断句

`>>` 换人与句末标点是**不可跨越**的边界：动态规划对每个终点先求出左侧最近的
强制断点，候选行首不得越过它。这样「两句并成一行」在结构上就不可能出现。

### 3.6 输出与时间钳制

- 行首若含该 cue 的首词，贴到 cue 起点；行尾若含该 cue 的末词，贴到覆盖 cue 的
  最大**真实**终点（被截断的 cue 用词估算终点，不贴它的滚动离场时刻）；
- 输出前向前钳制，保证时间轴严格递增（`createSrtLine` 的校验口径）。

实测效果（同一部 67 分钟视频）：

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| 重切分总时长 / 原 cue 总时长 | 1.50× | 0.67× |
| 首行起点 / 末行终点 | 0.0 / 4041.7 | 0.0 / 4041.9（与视频等长） |
| 行间时间重叠 | 大量 | 0 |
| 行首时间与源 cue 偏差中位数 | 2.64s | 0.85s |

总时长从「虚高 1.5 倍」回到与视频等长，是这条修复最直观的证据：多出来的那部分
正是每句都被重复计入的滚动尾巴。

## 4. 关键参数

| 参数 | 值 | 依据 |
| --- | --- | --- |
| `MAX_BLOCK_CHARS` | 220 | 无标点段落的强制封句上限 |
| `MAX_BLOCK_WORDS` | 40 | 词数上限，防止短词堆出巨块 |
| `MAX_BLOCK_SECONDS` | 12 | 单意群有声时长上限 |
| `MIN_SEGMENT_SECONDS` | 0.2 | 子区间最小时长，兼顾可点击性与严格递增校验 |
| `STRONG_PAUSE_SECONDS` | 0.6 | 视为强停顿时长 |
| `MEDIUM_PAUSE_SECONDS` | 0.3 | 视为中等停顿时长 |
| `LONG_LINE_CHARS` | 110 | 学习场景要完整句，阈值明显高于广播字幕的 42 |

调优建议：意群偏碎 → 提高 `BREAK_CUE` / `BREAK_HARD`；出现巨型合并 → 降低
`MAX_BLOCK_CHARS`；断句停在虚词上 → 检查 `DANGLING_WORDS` 是否缺词。

## 5. 为什么不直接结合音频

音频能给出真实停顿点，但有三个约束：

1. **词级时间戳优于音频**：本项目自建字幕（`SubtitleGenerationService`）走 ASR token
   时间轴，`EnglishSubtitleSegmenter` 已有词级 DP，精度高于任何声学推断；
2. **纯音频无法判断句意是否完整**：说话人常在从句中间停顿 0.5s，光看静音会把一句
   话切碎，必须文本 + 声学联合判断；
3. **解析层要求毫秒级、纯函数**：解码整条音轨是秒级到分钟级操作，不能阻塞字幕渲染。

因此当前版本**不接音频**，靠文本 + cue 时间戳完成断句。若后续要加声学增强，
应复用 `ProsodySignalService` 的能量包络管线，做成**懒加载 + 后台替换**：
先用纯文本结果立即渲染，包络算完后再静默替换，且必须保持播放位置与循环状态不变。

## 6. 接入点与缓存

### 6.1 接入点

`SubtitleServiceImpl.parseSrt`：`parseSrt/parseAss` 产出 `SrtLine[]` 之后、
`srtLineToSentence` 之前调用 `resegmentIntoMeaningGroups`。

`SplitVideoService` 直接调用 parser 纯函数（导出字幕保持原始 cue），不受影响。

### 6.1.1 转义残留必须在解析层清掉

YouTube 的 `.en.srt` 会夹带 ASS/WebVTT 的转义序列：

| 序列 | 含义 | 处理 |
| --- | --- | --- |
| `\h` | 硬空格（禁止在此断行） | 删除 |
| `\N` / `\n` | 硬/软换行 | 转成空格 |

它们在 SRT 里没有语义，是下载/转换环节漏出来的残留，但会被当成正文：
`you\h know` 原样渲染成 `you\h know`，用户看到的是莫名的脏字符与断行。

清理放在 `parseContentLines` 之前（`stripSubtitleEscapes`），这样意群断句、
翻译、跟读看到的是同一份干净文本。ASS 路径保留 `\N` 的换行语义，只删 `\h`。

### 6.2 缓存键

解析结果缓存于 `cache:srt`，**键一律是裸 `fileHash`**——翻译调度器
（`update-subtitle-demand`）、收藏片段、聊天会话、学习页等消费方全部按裸 `fileHash`
读取。键里掺任何前缀都会让这些消费方整体 miss。

缓存是进程内的，重启即清空，因此不需要版本标记或跨版本兼容处理。

### 6.3 翻译衔接

重切分后的行自带句末标点，是理想的翻译单元。翻译缓存按内容派生键，天然适配新行。

## 6.4 字幕轨优先级：作者轨 > ASR 轨

yt-dlp 对同一个视频可能下载到两份英语字幕：

| 文件 | 来源 | 特征 |
| --- | --- | --- |
| `xxx.en.srt` | 作者上传 | 有人工标点、时间轴不重叠、断句质量最好 |
| `xxx.en-orig.srt` | YouTube ASR | 无标点、cue 滚动重叠、需要重切分 |

旧实现用 `find` 取第一个匹配项，顺序取决于文件系统返回顺序——**同一个视频
有时挂作者轨、有时挂 ASR 轨**，用户会觉得「字幕对不上」时好时坏。

现在三处都统一按优先级选择（`preferred-track.ts`）：

1. **导入时**：`pickPreferredEnglishSubtitle` 选最优轨；
2. **播放解析时**：`WatchHistoryViewBuilder.resolveSubtitle` 发现当前挂的是
   ASR 轨、而同目录有作者轨时自动升级，并在 `SubtitleResolution.upgradedFrom`
   里带出原路径。已导入的视频无需重新导入即可受益；
3. **落盘同步**：`WatchHistoryService.playerSubtitle` 收到 `upgradedFrom` 后
   回写 `dp_watch_history.srt_file`，保证数据库记录与实际播放一致——
   否则下次扫描字幕、导出数据、按 `srt_file` 反查视频都会拿到过期路径。

回写失败不影响本次播放（升级已生效），只记 warn。

只做「ASR → 作者轨」这一个方向：已是作者轨、或用户手动指定了其他英语变体时不动。

实测某用户本地 7 个视频中，5 个都挂着 ASR 轨而作者轨一直躺在同目录没被用上。

## 7. 下游影响与接受的代价

| 消费方 | 影响 |
| --- | --- |
| 侧栏列表 / 主字幕 / 移动端 | 自动适应（同源 sentences） |
| 播放导航 / 循环 / 自动暂停 | 恒按意群块，行为统一，无开关 |
| 跟读练习单元 | 恒按意群块构建，播放区间额外加首尾留白（见 7.1） |
| 翻译缓存 | 旧碎片译文成孤儿行（无害，内容键不命中即弃） |
| 时间轴调整 / 配音 manifest | 按 fileHash-index 持久化，断句变化后行号失配即失效——**接受** |
| 收藏片段 | clipKey 按 ±5 行内容 hash，身份漂移但旧数据无损可播 |

### 7.1 练习片段必须包含完整的一句话

跟读 / 精听循环拿到的是 `[start, end]` 播放区间。**这个区间不能紧贴字幕边界**：

- 字幕边界是估算值（cue 起点常比真实开口略晚，词时间按音节比例插值）；
- 贴边起播会吃掉第一个音节的辅音，用户听到「半截开头」；
- 贴边截停会切掉尾音与自然停顿，听起来像被掐断。

`padPracticeClipRange` 统一加留白：句首 **120ms**、句尾 **200ms**（`practice-clip-range.ts`）。

只放宽**播放**区间，不改字幕行自身的 `start` / `end`——高亮仍按原边界走，
避免留白期间高亮提前跳到上一句。

覆盖范围：`playPracticeClip`（跟读）、`getLoopRange`（单句循环）、
`getVirtualGroupRange`（选区循环）。**自动暂停不加留白**：它只需要在句末停住，
不需要多播一段。

### 7.2 不保留历史兼容

项目尚未上线，**不做任何旧数据兼容**：

- 练习记录不再有 `resegmented` 维度，DB 迁移 `0025_drop_resegmented` 直接删列；
- 旧断句口径留下的练习记录语义上已无对应句子，随列删除一并清理，不做迁移或隔离；
- 学习数据导出/导入的 JSON 也移除了该字段。
